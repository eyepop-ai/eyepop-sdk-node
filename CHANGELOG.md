# Changelog

## [Unreleased]

### Changed

- `examples/webpack/src/world-demo.html` takes a dropped file as a source, not only a webcam. Whenever no live stream holds the pipeline, the video preview is itself the drop target — an image or a video dropped on it (or chosen by clicking it) runs through the same Pop, the same overlay, the same measurements and the same 3D tab, with the intrinsics rederived from what the file reports as its resolution rather than what a camera did. Hand-typed calibration values survive that, since only values the page derived are recomputed. A dropped video is stepped by its own results rather than played at real time: the preview is seeked to each prediction's `seconds` and only then drawn, so the overlay always belongs to the frame under it and one prediction is held rather than all of them — a worker is rarely exactly as fast as the media it is reading, and a scene cloud is megabytes a frame. Changing the feature or the calibration runs the loaded file again, since a still has no next frame to pick a new Pop up on. The drop target is enabled only while a session is open, and says so otherwise: the Pop runs on the worker, and a drop that quietly opened a session would make Connect mean nothing.
- The demo's camera selector, Start and Stop are one control: a selector of the cameras found, named "Connect webcam", while nothing is streaming, and a "Disconnect webcam" button while something is. The two are never both meaningful, so only one is on the page at a time. Connect is likewise a toggle — it reads "Disconnect" once a session is open — and carries a spinner while either is in flight, since opening a session takes seconds and disables everything it unlocks.
- Both of the demo's views carry a fullscreen toggle, overlaid on the view itself rather than placed beside it — the control belongs to the picture, and in fullscreen there is nowhere else for it to be. The video preview letterboxes its media inside the screen with the overlay canvas pinned to that rectangle rather than to the screen, so the drawing stays on the picture instead of spilling onto the black beside it; the 3D view simply fills the screen, its renderer following the container it already watches, and takes focus so the arrow keys keep working. Escape and the browser's own chrome are handled, since they leave fullscreen without going through either button.
- The demo's feature switch offers three Pops rather than two. **Point cloud** is now a Pop with nothing in it but a `depthMap` naming `eyepop.depth.metric.large-landscape` and asking for `toWorld`: no detector runs, the map itself is back-projected, and the whole scene arrives as one cloud — which is also what reveals the map, so the video tab draws it as a turbo heatmap through `renderDepth`. **Person point cloud** is what "Point cloud" used to be, a hidden SAM2 encoder behind a person detector with a component finder splitting each mask, its `erode` exposed. **Hand distance** is unchanged. Erode applies to the person clouds alone — the other two have no mask to shrink. The 3D view's cloud capacity rises to 520,000 points so the large map's 924x518 grid arrives whole, and the measurements panel lists per-carrier point counts for the two cloud features, where there is no distance to report.

### Fixed
- Name a real depth ability everywhere. The README examples and camera tests used `eyepop.depth.anything-3:latest`, which does not exist, and both `pop_demo` defaults used `eyepop.depth.large:latest`, which is not one of the four metric abilities and so would be accepted while silently producing no world coordinates. All of them now use `eyepop.depth.metric.small:latest`, and the READMEs name the full set — `eyepop.depth.metric.{small,small-landscape,large,large-landscape}`. The browser world demo keeps `-landscape`, which fits a webcam; the shipped example stills are portrait.

## [3.20.1] - 2026-09-10

### Added

- `response_schema` on the VLM ability types - `InferRequest`, `AutoPromptConfig`, `VlmAbilityCreate`, `VlmAbilityUpdate` and `VlmAbility`. Set it to constrain a VLM's output to a structured object matching the given Open API schema, which arrives parsed on each prediction's `details`. Typed as the exported `ResponseSchema`, an alias for `OpenAPIV3_1.SchemaObject` from `openapi-types` - a types-only dependency that adds nothing to the runtime bundle, mirroring the python SDK's use of `openapi-pydantic`'s `Schema` rather than leaving callers to hand-build an untyped object.
- Running Inference links out to the docs site's Sources and Options reference, which covers every source type and per-source option next to the Python SDK's equivalents.

### Fixed

- `Prediction.details` and `PredictedObject.details` are typed `Array<Record<string, any>>` rather than `Array<Map<string, any>>`, as are the `metrics`, `extra_params` and `auto_annotate_params` members of the dataset, model and evaluation types. All of them arrive through `JSON.parse`, which yields plain objects and never a `Map`, so the old declaration typechecked code that could only fail at runtime - `details[0].get('label')` compiled, and threw. Read them with index access instead.

### Removed

- `PopComponentType.TRACING`, the alias kept for pops serialized before 3.0.0. Nothing in the package referenced it. Use `TRACKING`.

## [3.20.0] - 2026-09-04

### Added

- World coordinates on predictions. `worldX`, `worldY` and `worldZ` (meters) now deserialise on key points, outline points and contour points, including cutouts - they are members of `Point2d`, so every carrier the worker enriches inherits them. Prediction v2 only, and a point the worker could not place carries none of the three rather than a zero or a NaN, so test for `undefined`. `Point3d.z` is untouched and independent: `z` is model-relative depth in whatever convention the model uses, `worldZ` is meters.
- `examples/node/pop_demo.ts --toWorld` adds world coordinates to any of its example pops, composed or flat: it names a depth ability and walks the component tree - nested `forward` targets included - opting in every component that can carry them. Hidden components are skipped, since their predictions never reach the response, while their targets are still walked. `--depthMapToWorld` asks for the scene cloud instead, or as well, and stands on its own: given neither a pop nor a model it builds the scene-only Pop rather than refusing for want of something to run. `--cameraHfovDegrees` or `--cameraIntrinsics`, with optional `--cameraRotation` and `--cameraTranslation`, supply the source calibration, and without one the demo says which guess the worker is falling back to. `--output` summarizes `world` payloads instead of dumping megabytes of base64, and reports how many points came back placed - which is what separates a calibration that worked from one that quietly did not. `--worldOut scene.ply` writes everything in the results that carries world coordinates to an ASCII PLY in meters - key points, outlines, contours with their cutouts, mask point clouds and the scene cloud alike, so a pop that produces no masks still has something to write. `cloudsOfPrediction()` finds the dense clouds only; the sparse carriers hold `worldX`/`worldY`/`worldZ` on the points themselves, and the demo walks those too, labelling each series by class and carrier and numbering a class that appears more than once. One colour per series, with the labels as header comments since a PLY has no notion of a series, and the points are joined by `element edge`: outlines and contours as closed rings in the order the worker emitted them, key points as skeletons through the renderer's own `POSE_CONNECTIONS`. A pair with an unplaced point in it is skipped rather than bridged, so a partially placed contour breaks where the hole is instead of drawing a line the geometry does not have. Viewers that ignore PLY edges show the points exactly as before. Points the worker could not place are dropped rather than written as the NaN a viewer reads as a corrupt vertex, and coordinates are rounded to a tenth of a millimeter, which halves the file and costs nothing a depth model could resolve. Open it in MeshLab, CloudCompare or Blender. There is still no node counterpart to the python `--visualize-world` plot: that one draws through `EyePopWorldPlot` in the SDK, and the node SDK has no world plotting API to draw through.
- `Mask.world`, the dense per-object point cloud, with `decodePointCloud()` and `cloudOfObject()` to read it: one xyz triple per mask pixel, indexed exactly like the bitmap. `PointCloud.at(i, j)` samples by mask pixel and `atSource(x, y)` by source coordinate, since the mask spans the object's bounding box. NaN is the wire's omission sentinel here and is preserved, unlike `decodeDepthMap()`, which rejects a malformed payload but has no NaN to keep.
- `Pop.depthMap` (`PopDepthMap`, with `ability` or `abilityUuid`) names the depth ability whose map the worker back-projects through, and `toWorld` on a component selects whose predictions get translated. `validatePop()` rejects a depth map naming neither or both, locally, rather than leaving it to come back as a 400.
- `PopDepthMap.toWorld` back-projects the map itself, so the results carry a point cloud of the whole scene rather than one per segmented object. It is also what reveals the map: without it the depth branch the Pop builds stays out of the response. It stands on its own - a Pop with nothing but a `depthMap` asking for `toWorld` is complete, no component has to opt in.
- `Depth.world`, the scene point cloud, read by `cloudOfDepth(depth, sourceWidth, sourceHeight)`. Same encoding as `Mask.world` but on the depth map's own grid, so `at(i, j)` lands on the index that pixel's value sits at in `Depth.values`. Both members ship: a NaN point says only that a pixel could not be placed, while the value at that index says why - `+Infinity` for sky, or a reading that is not a distance at all. `cloudsOfPrediction()` returns every cloud in one prediction, scene last.
- `Depth.semantic` says what a depth map's values mean: `canonical_metric`, `metric`, `relative` or `unknown`. Always present in prediction v2, so an absent member means a worker that predates the field rather than a map that declined to say. Only the two metric flavours can be back-projected.
- Camera calibration per source: a `camera` on `ProcessParams`, and in the Pop's `defaults`. `Camera` carries normalised intrinsics (`fx`, `fy`, `cx`, `cy` as fractions of the frame rather than pixels, so one calibration survives a resolution change) or an `hfovDegrees` shorthand, the OpenCV distortion coefficients, and a camera-to-world pose as a unit quaternion plus a translation in meters. Exactly one of `intrinsics` and `hfovDegrees` is required; both is rejected rather than resolved by precedence. `validateCamera()` runs before a source is submitted, so a bad calibration is an error locally rather than a 400 halfway through an upload. Without one the worker assumes a 60 degree field of view, which leaves lateral measurements exact and every distance along the optical axis wrong by however wrong that guess is.
- `examples/webpack/src/world-demo.html`, a browser demo of world coordinates end to end: webcam preview, camera selector, and a calibration panel, running 2d body points back-projected through `eyepop.depth.metric.small-landscape` and overlaying the distance in meters between each person's wrists, live, with a line joining them. The wrists stand in for the hands - the 2D body model has no hand point of its own. The Pop names a `depthMap` without `toWorld`, so the worker builds the depth branch and keeps it out of the response: on a live stream that is the difference between a few key points per frame and a megabyte of base64. Intrinsics are prefilled from the resolution the camera reports and an assumed field of view, using the same arithmetic the worker applies to the `hfovDegrees` shorthand, and the page says outright that they are computed rather than measured, since a browser never reports a focal length. `validateCamera()` runs before the stream starts, and a pose whose wrists were found but could not be placed is drawn dashed rather than dropped, so missing depth reads differently from a missing person. A feature switch above the calibration picks what the Pop runs: hand distance as described, or point cloud, which adds `eyepop.sam.small:latest` beside the body points and a component finder to split its mask, with the finder's `erode` exposed as an input. The mask is not drawn over the video in either mode - the 3D tab is where it becomes a cloud, alongside the skeletons. Switching applies through `changePop()`, so it works on a running pipeline rather than only before the stream starts. The page has two tabs: the video with that overlay, and a 3D view of the world coordinates themselves - three.js, with a Z-up axes helper, a ground grid at Z = 0 and orbit controls. The 3D tab draws every carrier the worker placed, not only the wrists: key points joined into skeletons through the renderer's `POSE_CONNECTIONS`, outlines and contours as closed rings, mask and scene clouds as points, one colour per series. Its buffers are preallocated and rewritten in place with the draw range moved rather than rebuilt per frame, since a new `BufferGeometry` every frame at 30fps is what turns a point cloud viewer into a garbage collector. Extrinsics are entered as yaw, tilt and height - a unit quaternion is not something to type by hand - with the quaternion actually sent shown beside them; left off, the coordinates come back in the camera's own frame, which the 3D tab states rather than leaving to be inferred. A pose does not change the measured distance, a rigid transform preserving distances, only where the points sit.
- `POSE_2D_CONNECTIONS`, `POSE_3D_CONNECTIONS`, `POSE_CONNECTIONS` and the `POSE_2D_CATEGORY` / `POSE_3D_CATEGORY` labels are exported from `@eyepop.ai/eyepop-render-2d`. They were module-private, so anyone drawing key points where the 2D renderer cannot reach - a 3D scene, a point cloud export, another canvas - had to copy the joint table, which is how two drawings of one skeleton come to disagree about where a wrist is. Joints are pairs of class labels rather than indices, so a model that emits its points in another order still draws correctly.

### Removed

- `examples/web`, the plain-script browser examples served straight off `python3 -m http.server`. They had gone stale against the SDK - `ingress.js` could not even connect, because `TransientPopId` is not one of the two names the webpack banner puts on `globalThis` and its member is `Transient` rather than `transient`, so Connect threw a `ReferenceError`. The webpack examples cover the same ground and are built against the local workspace, so they cannot drift from the SDK the same way. `upload` and `ingress` already existed there; `world-demo` is new.
## [3.19.1] - 2026-09-03

### Added

- Frame-level `depth` prediction member (`Depth` type) as produced by depth estimation abilities (e.g. `eyepop.depth.*`): base64 little-endian float32 map with the source frame's aspect ratio, sky pixels as `+Infinity`. `decodeDepthMap()` returns a `DepthMap` with typed values, finite min/max, and proportional source-coordinate sampling (`at()`, `isSky()`).
- `Render2d.renderDepth()`: turbo-colormap depth heatmap overlay (near = warm, far = cool, sky untouched by default), portable across node-canvas, browser, and react-native canvases.
- The `Mask` type is now exported from `@eyepop.ai/eyepop`.

### Fixed

- Compute session connection errors now preserve structured pipeline failure details from Compute API responses and sessions.
- Dataset event WebSocket failures now report the structured `EyePopDataWebSocketError` instead of rejecting with a raw browser event, and background reconnect failures no longer surface as unhandled promise rejections.
- Dataset event subscriptions are replayed after a reconnect; previously a reconnected session received only account-level events.
- The core package declares its direct `url-join` dependency, which previously reached the build only through workspace hoisting.
